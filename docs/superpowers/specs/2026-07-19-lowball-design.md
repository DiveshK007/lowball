# LOWBALL — Design Spec
**Date:** 2026-07-19 · **Program:** New Moon to Full: Monthly Moonshots on Midnight (Rise In)
**List primitive:** Sealed-Bid Auction (private bids, verifiable winner) · **Category:** Consumer focus
**Author:** Bond (solo, full-stack) · **Status:** Approved design, pre-implementation

> When you scaffold the repo, move this file to `docs/superpowers/specs/2026-07-19-lowball-design.md` and commit it as the first meaningful commit.

## 1. One-liner

Provably-fair mystery drops: name-your-price gacha where the reserve price is committed onchain before any bid, bids are sealed forever, and winners pay exactly what they offered. Priceline × blind-box mania × degen flex content — single-player vs the house.

## 2. Why this wins the program

- **Traction-shaped:** one user + one device. No coordination, no counterparty. 50 Preprod users = 50 strangers clicking a challenge link independently.
- **Primitive nobody else picks:** cohort-mates skip sealed-bid because "auctions need crowds." The house-as-counterparty (smart contract) removes the crowd requirement.
- **Privacy is load-bearing:** the game cannot exist without sealed bids and a committed hidden reserve. Not decoration — mechanic.
- **Content engine:** every drop is a post, every win is a flex card, every close is a receipts thread. Feeds the required X product profile.

## 3. Core loop

1. **Drop created** (admin): item (digital collectible record), stock (1 of N), hidden reserve price, close time. Only `hash(reserve, salt)` goes onchain, before any bid is possible.
2. **Player bids (sealed):** opens drop page → connects Lace → submits sealed bid. Bid amount is a private witness recorded as a commitment; no funds move at bid time (fallback funds path, §3.4/§10). Bids stay sealed for the whole window — nobody, including the house, learns any amount.
3. **The Reveal (drop closes):** house reveals `(reserve, salt)`; contract verifies it matches the original commitment. This is the appointment moment — countdown on the drop page, everyone comes back for it.
4. **Verdicts at reveal:** each bidder runs `checkWin` against the now-revealed reserve — proving bid ≥ reserve *without disclosing their amount*:
   - Cleared the reserve → **WIN at your price** (still never shown publicly). Pay on `claimItem`; unpaid claims expire (`CLAIM_GRACE`) and stock returns.
   - Under the reserve → nothing to do, nothing revealed. Losing amounts and near-misses stay sealed forever (comeback hook).
5. **Receipts:** public page shows commitment → reveal verification for anyone.

Rules: one bid per wallet per drop; if more bids clear the reserve than stock, **bid-order priority** (earlier sealed bids win — first-come spirit preserved). No highest-bidder ranking in v1 — YAGNI.

> **Changed at L1** (was: instant verdict at bid time). A bidder-side circuit cannot compare against a hash commitment without knowing the preimage, so a truly-blind instant verdict isn't achievable — verdicts land at reveal. Product upside: the reveal becomes a shared suspense moment (blind-box mechanics). See §10.

## 4. Privacy model (README "privacy model" section, verbatim target)

| Observer can see | Observer can NEVER see |
|---|---|
| Drop exists, item metadata, stock remaining | Any bid amount (including losing bids) |
| Reserve **commitment** (hash) | What a winner actually paid |
| Number of bids placed | How close a losing bid was |
| Winner claim proofs (item ownership) | Which wallet bid vs. merely browsed |
| Revealed reserve **after** close + match proof | House's reserve before close |

**Even the house cannot** see bids pre-verdict → cannot selectively accept or front-run. `disclose()` appears exactly twice in the codebase: (a) winner's item claim, (b) post-close reserve reveal. Narrative: *the only public things are the things that keep the house honest.*

## 5. Architecture

Three units, one repo (monorepo folders: `contract/`, `web/`, `ops/`).

### 5.1 Contract (Compact) — `contract/`
Single contract, circuits:
- `createDrop(commitment: Bytes32, stock: Uint, closeTime: Uint, metaRef: Bytes)` — admin-only.
- `placeBid(dropId)` — witnesses: `bidAmount`, `bidderSecret`. Inside circuit: check drop open + stock > 0; compare `bidAmount` against reserve via commitment scheme; on win decrement stock and record claim right; on loss trigger refund path. Shielded tDUST escrow in, kept (win) or returned (loss).
- `claimItem(dropId)` — winner discloses claim; item record assigned.
- `revealReserve(dropId, reserve, salt)` — post-close only; contract asserts `hash(reserve, salt) == commitment`; discloses reserve.

Ledger (public) state: drops map (commitment, stock, closeTime, metaRef, bidCount, revealed reserve), claims. Private state: bid amounts, bidder↔drop linkage.

### 5.2 Web app — `web/`
React + TypeScript + Vite + Midnight.js SDK + Lace DApp connector. Static hosting (Vercel). No backend server in v1 — the chain is the backend.

Screens: **Gallery** (live/past drops) · **Drop page** (the ritual: sealed-envelope bid animation → verdict reveal moment; this screen carries the entire product feel) · **My Shelf** (won items) · **/receipts/:dropId** (public verification page, no wallet needed) · **Onboarding** (Lace install → faucet → first bid in under 5 minutes, hand-held).

### 5.3 Ops — `ops/`
TS CLI: `create-drop` (generates reserve + salt, stores preimage in local encrypted file, submits commitment), `close-and-reveal` (submits reveal, posts receipts data). House keys never in the web app.

## 6. Testing & failure posture

Contract tests (L3 gate minimum, aim higher): win path · refund path · reveal-tamper rejection (wrong preimage must fail) · stock exhaustion · double-claim rejection · bid-after-close rejection.

App failure states handled explicitly: proof server down (retry + banner) · Lace absent (guided install) · tx timeout (persisted pending state, resume on reload) · drop closes mid-bid (graceful refund path).

CI: GitHub Actions — `compact compile` + full test suite on every push, badge in README.

## 8. Traction engine

Unit of growth = **the drop as content**. Post format: "🎰 Drop #N: [item]. Reserve sealed onchain. Lowball it." Win flow ends on a shareable flex card ("stole Drop #N for 12 tDUST 🤫"). Close flow ends on a receipts thread (reveal + verification link). Seed channels: Midnight/Cardano Discords, the program cohort itself (mutual-testing economy — LOWBALL is the easiest cohort dApp to try), CT replies on Midnight posts. Onboarding page owns faucet friction end-to-end.

## 9. Risks & mitigations

1. **Shielded escrow feasibility** — sealed-bid escrow assumes shielded tDUST transfer callable from a circuit with refund. **L1 includes a spike to verify this in the current SDK.** Fallback v1: commit-based bidding without real escrow (bid recorded as commitment; winner pays on claim; non-payment = claim expires and stock returns). Loop and privacy story survive intact.
2. **Reserve-preimage loss** — losing salt bricks a drop's reveal. Ops CLI stores preimages redundantly (local + encrypted backup); `closeTime` auto-expiry refunds bids on unrevealed drops so users are never stuck.
3. **Gambling optics** — losing bids always fully refund; no rake on losses in program version; items are collectibles, not wagers. State this in README.
4. **Solo-builder scope** — v1 cuts: no multi-bidder ranked auctions, no creator self-serve, no indexer, no accounts. Startup features come after L6.

## 10. Decisions log

- First-valid-bid-wins (not highest-bidder ranking) — instant verdicts beat auction-close suspense for single-player feel.
- Near-miss information never revealed — mystery drives re-bids; also simplest privacy story.
- Category: Consumer focus (Gaming defensible; Consumer chosen for startup framing).
- No backend server in v1 — chain + static hosting only.
- Name LOWBALL is a working title; collision-check before mainnet branding (L6).
- **2026-07-19 (L1):** Adopted spec §3.4 fallback funds path — `placeBid` records a bid commitment only; no shielded value moves at bid time. Shielded escrow deferred pending an L2 spike against Preprod. Reason: shielded primitives exist in stdlib but no stable dApp examples use them yet (see `docs/spikes/escrow-feasibility.md`).
- **2026-07-19 (L1):** `closeTime` stored on drop but *not enforced in-circuit* yet — deadline guards (`blockTimeLt`) land at L3 alongside claim + expiry paths. Reason: keeps L1 minimal per P1 scope; primitive availability already verified (see `docs/spikes/circuit-time.md`).
- **2026-07-19 (L1):** Single-drop-per-contract for L1 skeleton — no `drops: Map<DropId, …>` yet. Multi-drop support lands with L2/L3. Reason: keeps the L1 skeleton small enough to fully test the verdict machinery without paying map-syntax cost twice.
- **2026-07-19 (L1):** Verdict is computed at `checkWin` (post-reveal), not at `placeBid`. Reason: no known primitive gives a truly-blind verdict against a hash commitment without leaking the reserve to the bidder. **Product consequence accepted:** §3 rewritten from instant-verdict to reveal-day verdicts — the reveal countdown becomes the core engagement moment (blind-box mechanics). Frontend calls `checkWin` the instant the reveal lands so verdicts feel immediate *at* the reveal.
- **2026-07-19 (L1, spec):** Winner selection when multiple bids clear the reserve: bid-order priority while stock lasts (earlier sealed bid wins). Keeps first-come spirit; simplest to prove; no ranking.
- **2026-07-29 (L2):** Web uses an in-memory `PrivateStateProvider` (`web/src/lib/midnight/private-state.ts`) instead of the SDK's level-backed one, which cannot run in a browser (its `abstract-level` dependency extends node's `EventEmitter`). Consequence: witnesses live only for the duration of a call; the durable record is the user-owned bid journal in `lib/persistence`. No effect on the privacy table — less is persisted, not more.
- **2026-07-29 (L2):** The compiled contract bindings and ZK prover/verifier keys are committed under `web/src/lib/midnight/generated/` and `web/public/{keys,zkir}/` via `npm run sync:contract`. Reason: `contract/src/managed/` is git-ignored and the Vercel build has no Compact compiler, so the web deploy needs its own copies. Only `placeBid` and `checkWin` prover keys ship (~5.7 MB); `createDrop`/`revealReserve` are house-side.
- **2026-07-29 (L2):** Bids are journalled to local storage *before* submission, not after confirmation (architecture §5.2 pending journal). A pending record reconciles against the drop's `latestBidCommitment` on the next chain read, so a tab that dies mid-proof neither loses the secret nor risks a double bid.

- **2026-08-21 (L2/L3 unblock):** **Preprod deployed** — contract `1e7b6deedf3a04adb877416b845b8039c3cc5caf7b214cdaa532a8fce6263272`, deploy tx `0018b530…a6f632`, block 2,202,228, verified on the Preprod indexer as a `ContractDeploy`. This was the single requirement that failed both the L2 and L3 submissions. **Reached without a cloud VM**, contrary to the earlier assessment in `docs/spikes/preprod-sync-memory.md` that Preprod was infeasible on consumer hardware: the enabling change was `checkpointWhileSyncing()` writing the serialized wallet state every 5 minutes, which turned an all-or-nothing multi-hour genesis replay (~1.45M dust events + ~1.45M shielded coins, single-threaded and unshardable in the SDK) into a resumable *and portable* job. The sync was migrated four times between a 16 GB Mac and a 30 GB laptop, each time restoring rather than replaying. Two findings worth keeping: **(a)** restoring from a checkpoint produces a far leaner working set than replaying (post-restore RSS ~1.9 GB vs 10–11 GB while replaying), so the checkpoint doubles as a memory reset — which is why the 16 GB machine ultimately outran the 30 GB one; **(b)** the dust subscription can **freeze silently** — process alive, state ticks still emitting, applied counter frozen (observed ~8 min at 1,229,756) — so monitoring must watch for a stalled counter, not only for crashes; a restart from checkpoint clears it. Evidence: `docs/submissions/L1/03-preprod-deploy.md`.
- **2026-08-21 (bugfix):** `persistWalletCache` serialized all three sub-wallets with `Promise.all`, so a single failure discarded the entire checkpoint. In practice the **shielded** wallet intermittently threw `Could not serialize local state` (25 checkpoints succeeded, 15 were skipped), which meant losing the **dust** state too — the part representing hours of replay, and which had serialized fine. Now each sub-wallet is serialized independently via `allSettled` and any failure falls back to that wallet's previously cached value (shielded is ~4 KB and re-syncs in minutes; dust is megabytes and takes hours, so stale-shielded + fresh-dust is strictly better than no checkpoint). Only a wallet with neither a fresh nor a cached value aborts the write. Also made the write atomic (temp file + `renameSync`) so a kill mid-write cannot leave a torn 10 MB cache.

- **2026-09-05 (L4):** Began consolidating onto **one network, Preprod** — L1–L3 ran on Preview, and the Preprod address submitted for L2/L3 (`1e7b6dee…6263272`) turned out to be a **bare deploy with zero contract calls**: no drop was ever created on it, and the deployed app still read Preview. Consolidation is **not yet complete** — it is blocked on a Preprod wallet sync, and four findings came out of the attempt. **(a) The 2026-08-21 dust checkpoint no longer replays**: `values inserted non-linearly into dust commitment tree; expected to insert index 1075546, but received 1075567`. The error is raised and swallowed inside the SDK (`DustLocalState.replayEvents` → `RunningV1Variant`), so it never reaches `retryTransientSync` — nothing throws, no retry is logged, the applied counter simply freezes and `waitForSync` never settles. A run in that state looks healthy indefinitely; **diagnose by watching the counter, never by waiting for an exit**. **(b) Cache restore was all-or-nothing**, so one bad blob discarded all three ledgers. `startWallet` now restores per sub-wallet and `LOWBALL_RESET_DUST=1` drops only the dust blob — shielded (3.7 KB) and unshielded (1.6 KB) still restore instantly while dust (11 MB) replays. **(c) The default 4 GB V8 heap is the real ceiling for a dust replay**: it died with *Ineffective mark-compacts near heap limit* at 35,008/1,485,809 events with 62% of system RAM still free, and throughput had already collapsed to 147/min from GC thrash. `docs/spikes/preprod-sync-memory.md`'s conclusion that raising `--max-old-space-size` "only moved the OOM to the shielded phase" **no longer applies**, because with (b) shielded restores from cache and never replays — the two ledgers no longer compete for the same heap. Raised to 9 GB in the `deploy:preprod`, `create-drop` and `close-and-reveal` scripts; the crash point is passed. **(d) Dust checkpoints written by the current code do restore** — verified by killing a run and restarting without the reset flag: all three ledgers came back and dust resumed at 55,091 rather than 0. So the corruption in (a) is historic, not inherent, and the sync is genuinely resumable. Throughput still decays as the working set grows (~16,000/min at start → 508/min by RSS 3.6 GB), which is why the checkpoint doubles as a memory reset: restarting restores the lean working set and the fast rate.

Checking the built artefact, not the source, is what found it; that check belongs in any future network change.

- **2026-09-12 (L4/L5, multi-drop — reverses the 2026-07-19 L1 single-drop entry):** One contract now holds **many** drops, keyed by a `Bytes<32>` drop id. The L1 entry collapsed architecture §3.1's `drops: Map<DropId, …>` to a single slot deliberately, to test the verdict machinery without paying map-syntax cost twice. **That shortcut had become the binding constraint on L5/L6.** `createDrop` asserted the slot was unset, so every drop needed its own deployment — and since 2026-09-05 a deployment costs a full Preprod wallet sync, which is hours. Worse for the program: L5 needs 50 users and L6 needs 70, bidding over weeks, and one drop per contract **fragments the on-chain evidence of that userbase across a dozen addresses**, leaving no single contract that demonstrates it. **Shape:** flattened sibling maps (`dropStatus`, `dropCommitment`, `dropStock`, `dropCloseTime`, `dropMetaRef`, `dropBidCount`, `dropLatestBid`, `dropRevealed`, `dropWinnerFound`) plus a `dropCount` counter, rather than one `Map<DropId, struct>`. A struct value reads tidier but forces a whole-record read-modify-write on every bid, and a `Cell` read **commits the transaction to that field's current value** — so two bidders in the same block would collide, precisely under the concurrency L5 exists to demonstrate. `Counter.increment` carries no such constraint. Flattening also keeps the ledger readable by indexers that cannot decode structs. **The drop id is the slug as UTF-8, zero-padded to 32 bytes** (`drop-002`), so contract, ops and browser derive the same key with no circuit call and `/drop/:dropId` URLs keep working. **Three Compact facts worth keeping:** a `lookup` of a missing key is a *dynamic error*, not an empty value, so every read needs a `member()` guard; nested ledger values must be initialised (`default<Counter>`) before first use; and a `Counter` nested in a `Map` comes back to TypeScript as its ADT, so it reads via `.read()`, not as a bigint. **Deployed** to Preprod at `edae325517131cd6dbfdf953cf87cf3ef337191b1ef50f12a9f1a57dab468dc7`, block 2,519,627, carrying **two** drops — `drop-001` (Genesis Envelope) and `drop-002` (Second Envelope) — both open until 2026-11-01, deliberately well past the end-of-September judging window. Verified by decoding the contract state (both drops present) and by fetching the deployed JS chunks (1 occurrence of the new address, 0 of the superseded one). **Deliberately deferred:** architecture §3.3 also binds `dropId` into the reserve commitment (`H(reserve || salt || dropId)`). Changing `reserveHash` would invalidate the fixture in `web/src/lib/midnight/hashes.test.ts`, which is anchored to a commitment the chain has already accepted — and that anchor is what makes the receipts page's arithmetic checkable. Rebinding needs a fresh chain-accepted commitment to re-anchor against, so it follows this deploy rather than preceding it. **Now the next blocker:** `dropLatestBid` still records only the *most recent* bid per drop, so only the latest bidder can pass `checkWin`. Harmless at L4 with one bidder; at L5 it means 49 of 50 bidders cannot win. Fixing it needs a set or Merkle accumulator of bid commitments plus a membership proof in `checkWin`, and should be the next piece of work. Plan: `docs/superpowers/plans/2026-09-12-multi-drop.md`.

- **2026-09-12 (L5, bid accumulator):** **Every bidder on a drop can now prove their own win.** `placeBid` wrote into `dropLatestBid: Map<DropId, Bytes<32>>` — one slot per drop, overwritten by each new bid — and `checkWin` compared against it, so **only the most recent bidder could ever pass**. At L5's 50 bidders that is 49 failures, and silently indistinguishable from losing: an overwritten bidder and a losing bidder got the same message. It also broke the web's crash recovery, which reconciled a journalled bid against `latestBidCommitmentHex` and so left every non-latest bidder stuck on *pending* forever. **Shape:** `dropBids: Map<Bytes<32>, Set<Bytes<32>>>` accumulates every commitment; `dropWinners: Map<Bytes<32>, Set<Bytes<32>>>` records which ones claimed. `dropLatestBid` and `dropWinnerFound` are gone — the latter because `dropWinners.size() > 0` says the same thing and cannot drift out of step with it. `dropBidCount` stays: it counts *submissions* where `dropBids.size()` counts *distinct* commitments, and the gap is real information. **Set, not Merkle, and the deciding argument was correctness, not simplicity.** A plain `MerkleTree` root moves on every insert and Compact's `MerkleTree` does not permit proofs against past states — so a bidder who computes a path, then waits out a proof and a signature, races every bid submitted meanwhile and lands with a stale path. At 50 bidders that is the normal case, not an edge case. `HistoricMerkleTree` fixes it but means historic roots, per-bidder leaf indices and off-chain path computation shipped into the browser. A `Set` is order-independent, checks membership directly in-circuit, and nothing a bidder holds goes stale. The usual reason to prefer Merkle — keeping the set off-chain or hidden — does not apply: bid commitments were **already public** in `dropLatestBid`, the set size was already public via `dropBidCount`, and 50–70 32-byte entries is nothing. The zero-knowledge property is unchanged and lives where it always did: `amount` and `secret` stay witnesses, so the proof says *"the commitment I can open is in this drop's bid set and the amount inside it clears the revealed reserve"* without disclosing either number. **New guard:** `checkWin` rejects a commitment already in `dropWinners` ("win already claimed"), so a winner cannot inflate the winner count by re-running it — that count is what L5/L6 evidence rests on. **Verified on Preprod, not asserted:** contract `72dfe0295bb744874f6b5a7ed961f2b5dd4b883666f7dd87d4fd2260f169a4b1` (block 2,520,320) carrying three drops; on `drop-proof`, **three distinct bidders placed sealed bids and all three passed `checkWin`** — the ledger shows 3 submissions, 3 distinct commitments and **3 winners**. `drop-001` and `drop-002` stay OPEN until 2026-11-01 for judging. **Process bug found the hard way, now fixed.** The first deploy of this change silently shipped the *previous* contract: `contract/scripts/deploy.ts` imports the `Contract` class from **`ops/managed/`** (on purpose, so Contract and compact-js share one runtime tree), and recompiling without re-running ops' `sync:contract` leaves that copy stale. Nothing failed at deploy time — it surfaced only when bidder 1's `checkWin` threw *bid preimage mismatch* against a contract that still had the single-slot logic. `predeploy:preprod` and `pre{create-drop,close-and-reveal,simulate-bidders}` now run the sync, so a stale deploy is no longer reachable. **Also seen:** one transient `key (segment_id) collision during intents merge` when a call started immediately behind another wallet session; re-running it alone succeeded. Treat wallet sessions as strictly sequential. **Still deferred:** stock is not decremented on a win, so every clearing bidder wins. Architecture §3.3 specifies `on WIN: stock -= 1`, and enforcing it needs a rule for which clearing bidders win when there are more than stock — bid-order priority per the 2026-07-19 entry. That is a product decision, it is in direct tension with this pass's own acceptance test (three bidders winning one drop), and it is the next open question rather than something to choose silently. Plan: `docs/superpowers/plans/2026-09-12-bid-accumulator.md`.

- **2026-09-12 (L5, stock enforcement — reverses the 2026-07-19 bid-order-priority entry):** Stock is now enforced by **claim order**: `checkWin` succeeds only while `dropWinners.size() < stock`, so the first `stock` bidders to *claim* take the units. The original rule — *"bid-order priority while stock lasts (earlier sealed bid wins)"*, also written into architecture §3.3 — is **not merely being changed, it is unimplementable under this product's own privacy claim**, and that is worth stating plainly because it looked reasonable for two months. **Why it cannot be built.** To decide whether bidder X wins under bid-order priority, the circuit must know **how many earlier bidders also cleared the reserve**. Whether an earlier bidder cleared is a fact about *their bid amount* — which is their private witness and exists only on their device. The ledger holds only `hash("lowball:bid:v1", secret, amount)`, and a hash cannot be compared against a reserve. That leaves three routes and all three fail: **(a)** have X's circuit read other bidders' amounts — they are not available to X at any price, and the whole point is that they never leave their owners' devices; **(b)** have the house hold or decrypt the amounts to rank them — this breaks the headline claim that a bid is never disclosed *to anyone, including the house*, which is the one sentence the product is built on; **(c)** have each bidder prove their own clearing status and then order those proofs — but the only order available to the chain is the order the proofs **arrive**, which is claim order, not bid order. Route (c) is what we have implemented, and naming it honestly is better than pretending it approximates the original rule. **What claim order costs and buys.** Cost: sealing a bid early no longer secures a unit, so a bidder who bid on day one can be beaten by one who bid an hour before close but claimed faster. Buy: it is enforceable with public state alone (a winner count against a stock number, both already public), it discloses nothing new, and it turns reveal-day into a race — which suits the blind-box mechanic the L1 verdict decision already pushed us toward, where the reveal is the engagement moment. **Assert order matters and is deliberate:** the sold-out check sits *after* the reserve check, so a bidder who did not clear is told "bid below reserve" and a bidder who did clear but arrived late is told "drop sold out". Conflating them would tell losers they might have won. Both messages are produced by a local assert failure — nothing is submitted and nothing is disclosed on chain either way. **Concurrency:** reading `dropWinners.size()` ties the transaction to the winner count it was proved against, so two claims for the same last unit cannot both be applied — the loser's transaction fails validation rather than the drop overselling. That is the expected mechanism from Compact's ledger-read semantics; it has not been exercised with genuinely simultaneous submissions, only sequentially. **Verified:** 27 contract tests including five clearing bidders against a stock of three producing exactly three winners, a stock-1 drop selling out after one claim, and repeated claims never exceeding stock. The web maps the assert to a `drop-sold-out` error rendering as *"This drop sold out."* with the hint that the bid cleared but the last unit went first.

- **2026-09-23 (L5, 1AM wallet support):** Added **1AM** alongside Lace behind a wallet picker, and switched proving to the connector's `getProvingProvider` when a wallet offers it. Both wallets are discovered by scanning `window.midnight` (Lace injects at `mnLace`, 1AM at `'1am'`); `selectWallet` only auto-connects when exactly one compatible wallet is present, so a user with both is always asked. `ZKConfigProvider.asKeyMaterialProvider()` bridges our `FetchZkConfigProvider` into the connector, and `createProofProvider` adapts the result back into a midnight-js `proofProvider` — no custom shim. Lace does not implement `getProvingProvider`, so this is a **feature detection with a fallback**, not a version check: if the call is missing or throws, we fall back to the local proof server. **The premise that 1AM sponsors DUST is false, and checking it mattered.** The brief assumed 1AM handles "ZK proving and DUST sponsorship in-browser", which would have meant a zero-DUST onboarding path. Four sources say otherwise: Midnight's wallet overview (*"1AM has not documented automatic fee sponsorship, so do not assume a zero-DUST experience"*), the functionality matrix (gas sponsorship: *not documented*), the integration guide (*"sponsorship is a capability the connector allows, not a guarantee that any given wallet ships"*), and **1AM's own FAQ** (*"You need NIGHT to generate DUST for transaction fees"*). The connector's `payFees` option defaults to true, but that makes the wallet a relayer paying from the **user's own** DUST — not a sponsor. So 1AM removes the **proof server**, not the DUST setup, and the docs say exactly that. Shipping "no DUST setup needed" would have stranded every L5 tester at the fee step. **Preprod is supported** — confirmed via the 1AM forum guide (*"all Midnight networks (Preview, Preprod, and Mainnet)"*), which was the gating question. One caveat kept in code: only `'mainnet'` is a connector-standard network id, every other id is wallet-defined, so a connect refusal now surfaces as a named network-id mismatch rather than a generic failure. **A shipped documentation error surfaced while doing this:** `docs/USAGE.md` claimed the app "uses the prover built into Lace, so you do not need Docker". Lace has no built-in prover and requires a local proof server — the guide would have stranded every Lace tester. Corrected, with the proof-server command in the guide and 1AM recommended precisely because it avoids that step. **Not verified end to end.** The zero-DUST acceptance test in the brief is not achievable, and the rest needs a human with the extension installed: no 1AM extension exists in this environment, so the picker, the in-browser proving path and the network-id string 1AM actually accepts are **unverified against a real wallet**. The code is feature-detected and falls back, so a Lace user is unaffected either way.
